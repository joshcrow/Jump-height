# Adversarial audit — 2026-08-22 (work orders)

Findings from two adversarial audit sweeps over the working code: one for
correctness/rigor (29 agents), one for quality/optimization/maintainability/
efficiency (33 agents). Every finding below survived an independent skeptic
instructed to refute it; findings marked **hand-verified** were additionally
reproduced by the orchestrating session (compiled, disassembled, timed, or run
against the repo's own harness).

**Authority note:** `docs/STATUS.md` remains the authority on current device
truth. If this document and STATUS.md disagree, STATUS.md wins and this
document is stale — fix it.

**Status tracking:** check the box and add the commit hash when a ticket
lands. A ticket is done when its acceptance test passes, not when the diff
exists.

## Standing instructions for any agent working these tickets

1. **The dominant defect pattern in this codebase is site-local fixes** — a
   correct pattern applied where it hurt and not to its siblings (five
   confirmed instances across five subsystems). Every fix below MUST end with
   a sibling sweep: grep for the same shape elsewhere; fix or explicitly clear
   each hit **in the same commit**.
2. **Batch firmware changes into one flash** (CLAUDE.md rule 4). Phases 1–2
   below are one flash batch.
3. **No verdict without a measurement; retracted figures stay retracted**
   (CLAUDE.md rules 2–3). The current-draw baseline is the conservation bound
   ≤9.7 mA (250 mAh / 25.7 h). 11.6 mA and 16.3 mA are retracted.
4. **Verify each finding against source before coding.** Several
   originally-raised findings were wrong; the refuted list at the bottom
   exists so you don't re-chase them.
5. **Pin boards by name** (`--name JumpHeight-XXXX`). Only the OG
   (`JumpHeight-E2C4`) has a battery. See `docs/bench-playbook.md` §1.

## WS1 — Build & gate integrity (P0 — do first and alone)

Every later fix is validated by these gates; until they are honest, green
means nothing. Theme: a test that passes on a binary that isn't the one that
ships.

### [x] F-01 · **LANDED 8fa4e15** · major · hand-verified — -Ofast deletes the isfinite() guards

- **Location:** `firmware/platformio.ini:42-67`, guards at
  `firmware/include/trace_codec.h:154` and
  `firmware/src/platform/nrf52/jh_store.cpp:980`
- **Defect:** `[env:xiaoblesense_adafruit]` sets no `build_flags`, so the
  Adafruit builder default `-Ofast` wins (`adafruit.py:86,131` in the pinned
  platform). `-Ofast` implies `-ffinite-math-only`: `if (!isfinite(mag_g))
  return 0;` folds to constant-true. Host tests asserting the guard compile
  without -Ofast — they pass on a different binary than the one that ships.
- **Evidence:** disassembled both ways: `-Os` emits a real compare
  (`andps/ucomiss/setae`); `-Ofast` emits `mov $0x1,%eax; ret`. Replicated on
  the project's pinned GCC 7.2.1 ARM toolchain. `-Os` image measured
  42,288 B smaller (177,732 B → ~135 KB), paid on every OTA.
- **Fix:** add `build_flags = -Os` (or `-O2 -fno-fast-math`) and
  `build_unflags = -Ofast` to the target env. Rebuild; confirm the guard is
  present in the .elf (`objdump -d | grep -A4 milli_g_from_g`); confirm size
  drop; re-run the desk three-toss on the OG before trusting numeric behavior
  (fp-contraction differences are possible — that is the point).
- **Acceptance:** shipped .elf disassembly shows a conditional at both
  isfinite call sites; the flag lives in platformio.ini so a platform update
  can't silently revert it.
- **Sibling sweep:** grep firmware for NaN/Inf-dependent logic (`isnan`,
  `isfinite`, NaN-trap comparisons) — each was dead under -Ofast and becomes
  live after this change.

### [x] F-02 · **LANDED 9913b4a** · major · hand-verified — simtest runs 137 of 191 tests

## WS2 — Power (P0 — same flash batch as WS1's firmware change)

The largest measured lever in the repo. Baseline discipline: current baseline
is the conservation bound ≤9.7 mA; 11.6 mA is retracted.

### [x] F-05 · **LANDED 3079f96** · major · hand-verified — DC/DC never enabled at boot

- **Location:** `firmware/src/main.cpp:766` (only call site), `setup()` at
  `main.cpp:1143-1207`; evidence `docs/STATUS.md:1016-1052`
- **Defect:** `sd_power_dcdc_mode_set(NRF_POWER_DCDC_ENABLE)` is reachable
  only via the `dcdc` console command. setup() never calls it; DCDCEN is
  volatile, so every boot is LDO and every watchdog reset (which StoreGuard
  deliberately produces) silently reverts a hand-typed enable. No wire field
  reports the mode.
- **Evidence:** repo's own same-board A/B (STATUS.md:1023-1025): 5.58 h /
  5.49 h baselines vs 7.70 h with DC/DC → 1.39× endurance ≈ 0.72× current.
  STATUS.md:527's gate ("earns a place in boot only after the A/B") was
  satisfied 2026-08-20; code unchanged. The Adafruit core never enables it
  behind the app's back; both boards' inductors proven populated
  (STATUS.md:511-521).
- **Fix:** in setup(), after the SoftDevice is confirmed up (reuse
  jh_power::init()'s `sd_softdevice_is_enabled()` pattern — POWER is
  SoftDevice-owned, see STATUS "Trap 1"), enable DC/DC. Add `dcdc=0|1` to the
  stats/info line. Keep the console command as bench override.
- **Acceptance:** stats reports dcdc=1 after cold boot AND after a forced
  watchdog reset; next OG discharge night moves toward the projected
  ~20 h → ~30 h on the 4.10→3.50 V window (STATUS.md:1052).

### [x] F-06 · **LANDED c99a5d9** · major · skeptic-confirmed — pacer guard band busy-spins

- **Location:** `firmware/src/main.cpp:1325`
- **Defect:** `if (next_us - now_us > 1200) delay(1);` — below 1200 µs
  remaining, loop() never blocks, the idle task never runs, the core spins at
  64 MHz. The "final tight approach" premise is void: `micros()` on this core
  is tick-derived (976.5625 µs steps, confirmed by disassembling the built
  object), so the spin buys zero precision. Measured ~24% of wall-clock spent
  spinning.
- **Fix (preference order):** (a) enable the DWT cycle counter at boot — the
  core's micros() upgrades itself to CYCCNT/64, making the band honest and
  shrinkable to ~1050 µs; (b) keep the tick clock, drop the guard to one tick
  (`> 977`), accept ±1 tick jitter — the pacer's own math (dh = g·T·dT/4 →
  2.5 mm at 1 s flight) already argues this is negligible.
- **Acceptance:** the falsifier the comment names: post-change sample deltas
  within 2 ms of cadence; desk-test airtimes show no systematic shift.
- **Sibling sweep:** audit the other 32 `delay()` sites for spin-adjacent
  waits; most are boot/bench paths and fine — document, don't churn.

## WS3 — Storage & device data integrity (P1)

The store's happy path and torn-write recovery are excellent (85/85
randomized power-cut trials held). These are the edges the discipline missed.

### [x] F-07 · **LANDED 81a3a2d** · major · skeptic-confirmed (reproduced in harness) — trace_clear() appends after failed erase

- **Location:** `firmware/src/platform/nrf52/jh_store.cpp:1143-1178`
- **Defect:** the descending erase loop accumulates `all_erased` but never
  breaks on a failed sector; on failure it leaves `s_fs_ok` true and
  re-derives an append point that structurally cannot see the stale island
  above it — the mirror image of the power-cut layout the adjacent 40-line
  comment defends against. NOR AND-merge then corrupts silently. Contrast:
  `clear()` at :1253 handles its erase failure correctly — the site-local-fix
  pattern again.
- **Evidence:** reproduced with the repo's own harness using
  FAIL_NEXT_ERASE: post-failure append lands under a stale block; readback
  interleaves old and new samples.
- **Fix:** on any eraseSector failure in trace_clear(): stop, mark the trace
  region unusable for append (mirror clear()'s `s_fs_ok = wrote_sb`
  discipline, scoped to trace), surface it on the wire (`ERR trace_clear`).
  Add a FAIL_NEXT_ERASE test asserting append refusal.
- **Landed:** `81a3a2d` — break on the first failed sector; `s_trace_wedged`
  refuses `trace_append()`; `trace_wedged()` added to the seam (both impls) so
  callers can ask instead of assuming; `ERR trace_clear` on the wire.

  **Reproduced first, in the repo's harness** — the pre-fix run reported
  `TRACE_CLEAR ok=1`, `TRACE_BYTES n=0`, then an append that SUCCEEDED into a
  region still holding 280 KB of samples. Post-fix the same script gives
  `TRACE_CLEAR ok=0 wedged=1`, `n=279306` (honest), and the append is refused;
  `JUMPS_SCAN count=1` confirms the wedge is scoped to trace and does not cost
  the rider their results.

  **The ticket understated the fix.** `s_trace_wedged` is RAM, and a failing
  flash chip is precisely the thing that causes watchdog resets on this board
  (measured, twice, on the mule). One reset would clear the flag and the next
  mount would re-derive an append point with the same blindness — so the fix
  as written would have evaporated exactly when it mattered. Added
  `jh_persist::Key::TraceGuard` (bit 2 of the existing v3 guard byte, no record
  migration) restored at boot and cleared by `format`/`clear`, following the
  `StoreGuard` bracket main.cpp already owns.

  **Acceptance:** `TraceClearEraseFailure` in `tools/tests/test_store_host.py`.
  Mutation-tested three ways — deleting the append guard, restoring the
  original no-break erase loop, and making `trace_wedged()` report healthy —
  all three kill the test. simtest 192/192 PASS.

  **Sibling sweep (the `&=`-accumulate-and-continue shape):** three erase
  sites in firmware. `eraseChipFed():649` already returns at the first failure
  — clear. `clear():1259-1271` uses the same accumulate-and-continue shape but
  fails SAFE: `s_fs_ok = wrote_sb` gates both append paths (`:1009`, `:1041`),
  so no write follows a failed erase — left as-is. `trace_clear()` was the only
  site that both continued past a failure AND re-enabled appends, because it
  deliberately does not touch `s_fs_ok` (a trace problem must not take the
  jumps region down). That asymmetry is why it needed its own flag.

  **NOT proven on silicon.** The reboot-restore path is verified by code
  review plus confirming both strings survive into a clean-built ARM image; a
  real failed sector cannot be forced on a healthy chip. It rides the F-08
  flash batch — desk-check `format` clears the wedge line at boot.

### [x] F-08 · **LANDED a30453e** · major · hand-verified — mount formats ~940k samples for a display-only counter

- **Location:** `firmware/src/platform/nrf52/jh_store.cpp:441` (also :216
  `csvLineLen`, :362 `csvByteCounter`)
- **Defect:** `findTraceAppendPoint()` rebuilds `s_trace_csv_bytes` by
  snprintf-formatting every stored sample. The counter is display-only.
- **Evidence:** measured on the repo's own harness (real jh_store.cpp,
  g++ -O2): full chip (14.46 MB, 938,500 samples) mounts in ~320 ms vs
  1.2 ms empty; isolated snprintf benchmark = 297.9 ms (93%) and its
  accumulator (14,460,500) matches TRACE_BYTES exactly. On the M4F at 64 MHz
  with softfloat `%f`, plausibly seconds per boot.
- **Fix:** persist the counter — store cumulative csv-bytes (or per-block
  totals) in the block header or superblock at write time; on mount, sum
  headers. Keep one debug command that recomputes the slow way for
  cross-checking. Block-format changes must be batch-flashed (rule 4) and
  keep decode compatibility with already-written blocks — version the header.
- **Acceptance:** full-chip mount in the harness within ~10× of empty-chip;
  parity test proves stored counter == recomputed counter over a fuzzed
  store.
- **Landed:** `a30453e` — 221 ms → **74 ms** full-chip mount (0.93 ms empty).

  **No block-format change, so NO second flash batch** and no field-
  compatibility question. Phase 3's plan assumed one; it is not needed. A floor
  probe decided it: replacing the counter with a *no-op* still cost 60 ms,
  because the scan must read and CRC every block to find the append point and
  recover torn writes. Persisting totals in block headers — the fix the ticket
  proposed — could not have beaten that floor either. The snprintf was the only
  removable cost.

  `csv_line_len()` lives in `trace_codec.h` beside `emit_csv_sample()`, the
  function whose output length it predicts.

  **The first implementation was wrong, and the sweep caught it before it
  shipped.** `llround(fabs(v) * 1000.0)` fails on x.xxx5 edges: 9.9995's
  nearest double is 9.99949999999999938 (printf: `"9.999"`), but the multiply
  rounds the product to exactly 9999.5 and llround takes halves away from zero
  — one digit too many, 12 values. Now compares the fractional part directly,
  which is exact: `modf` is exact and 0.9995 is not representable, so no double
  lies between the true value and the literal.

  **Cross-check kept:** `trace_bytes_recomputed()` / the `tracecheck` command /
  harness `TRACE_RECHECK`, reusing the SAME walk (factored out of
  `findTraceAppendPoint()`) so it tests the real traversal, not a second
  implementation checking itself.

  **Acceptance — one half met, one half not.** Parity: proven both ways
  (`TraceCsvByteCounterParity` over fuzzed stores; on the full chip 14,475,206
  identical). Mount ratio: **~80× empty, not ~10×** — and ~10× is unreachable
  by ANY counter scheme, since the 60 ms floor is the walk itself. Filed as
  **F-23** rather than quietly restating the target.

  **Why a second test exists:** the store-level parity test *cannot* prove the
  arithmetic. Everything on flash is quantized to the k/1000 lattice, so a
  truncate-instead-of-round mutant survives it and negatives never occur.
  `CsvLineLenSweep` does 400,132 direct comparisons including negatives and
  off-lattice values; all mutants die there. The lattice is why the fast path
  is safe in production and why production data can't test it.

  **Two earlier versions of the store test were vacuous** — comparing
  in-process (`fast=30 slow=0`: the live counter includes the still-open block)
  and comparing two-sample appends (a block holds 255, so it compared 0 == 0
  and reported "agree").

### [x] F-09 · **LANDED b3cd92d** · major · skeptic-confirmed — pincensus leaves the bus down, prints "revive ok"

- **Location:** `firmware/src/main.cpp:702-708`; `jh_imu.cpp:164-219`
- **Defect:** the handler calls `jh_imu::revive()`, which begins with
  `bus_release()` (→ `s_bus.end()`, `begun_=false`), rail-cycles, and returns
  true unconditionally — no `s_bus.begin()`, no `s_imu.begin()`. Every
  subsequent read returns BUSERR; sensor_ok stays true; the session records
  nothing. The `revive` command recovers correctly (runSelfTest → probe →
  begin); pincensus doesn't. The one-shot warning at :1345 uses strict
  equality (`== 200`), so it can be pre-consumed by earlier transient
  failures.
- **Fix:** after the census revive, run the same recovery chain the revive
  command uses (or call runSelfTest() and report its verdict instead of
  "ok"). Sibling sweep for rule 3: change the fail-count gate from `==` to
  `>=` with a latched flag.

### [x] F-10 · **LANDED 0c222b7** · minor · skeptic-confirmed — jumps_append() void with silent refusals

- **Location:** `firmware/include/platform/jh_store.h:74-80`;
  `nrf52/jh_store.cpp:805,806,848-851`; `main.cpp:1500`
- **Defect:** three refusal paths are bare returns; main.cpp increments
  stored_jumps unconditionally. The user-facing double-count was REFUTED
  (jumps list re-derives from flash) — this is interface debt, the seam that
  keeps generating F-09-shaped bugs.
- **Fix:** return an enum status (OK / FS_DOWN / FULL / TORN_RETRY); main.cpp
  counts only OK and emits one line on first refusal. Update the host
  implementation and the harness in the same commit (the seam has three
  implementations: nrf52, host, mock).
- **Landed:** `0c222b7` — `AppendResult{OK, FS_DOWN, REGION_FULL, WRITE_FAILED}`;
  main.cpp counts only OK and narrates the first refusal per outage
  (`scanStoredJumps()` re-arms it).

  **Ticket correction:** the seam has TWO implementations, not three — nrf52
  and host. `firmware/test/store_host/` is a *caller* of the nrf52 one, not a
  third implementation.

  **The harness had the defect it exists to detect.** `JUMPS_FILL` ran
  `++appended` unconditionally, so a refused fill still reported the full
  count, and `JUMPS_APPEND` printed `done=1` for appends that were refused.
  Both fixed — no test depended on `done=1`. This matters for F-19(b), whose
  region-full test would otherwise have asserted against a lying counter.

  **Sibling sweep — the same shape in `jh_persist`.** `writeRecord()` was void
  and swallowed three failure paths (open, short write, rename); `save()` and
  `clear()` discarded it under a documented "no failure path to report"
  contract. Defensible when the only keys were calibration numbers a human had
  just typed; not defensible once the guard BITS moved in — `ProbeGuard`,
  `StoreGuard`, `TraceGuard` are safety flags whose job is to survive a reset.
  Both now return bool, and main.cpp checks the `TraceGuard` save (F-07's
  persistence depends on it) and warns if the flag did not take.

  **Acceptance (all mutation-tested):** `JumpsAppendReportsStatus`
  (`test_store_host.py`) and `TestStorageRefusalIsVisible` (`test_hostdev.py`
  — end-to-end through the host binary with a read-only store dir: two real
  scripted jumps, `session_jumps=2`, `stored_jumps=0`, exactly one warning).
  simtest 195/195 PASS.

  **Note on the first attempt:** the fill test was initially written against a
  fill that succeeds, which passes with the counter still broken. Rewritten to
  drive a real refusal. `HostDevice` gained a transcript because `wait_for()`
  drops non-matching lines, so the warning between two JUMP lines was
  unassertable.

### [x] F-11 · **LANDED 18e718f** · major · hand-verified — JUMP path drives session count/best DOWN into the FIT

- **Location:** `garmin/jumpfield/source/Model.mc:238-239` (correct guard
  exists at :308-310)
- **Defect:** the JUMP path assigns `_sessionBestM`/`_jumpCount`
  unconditionally from the wire; the 2026-08-21 monotonic guard covers only
  the STATS path (and best-airtime). Firmware session counters are RAM
  statics (`main.cpp:132-134`) that reseed on brownout, so
  `JUMP n=1 … best_m=0.20` after a 12-jump session is a legal line that
  `_jumpIsCorrupt` cannot reject; JumpFieldView.compute() pushes it into
  FitOut.updateSession() at ~1 Hz. The comment at :304-306 diagnoses this
  exact pattern and then repeats it.
- **Fix:** apply the same monotonic guards on the JUMP path
  (`n > _jumpCount`, `b > _sessionBestM`, same sanity-bounds family).
- **Acceptance:** unit test in `garmin/jumpfield/tests` feeding a
  reboot-reseed sequence (n=12,best=1.05 → n=1,best=0.20) asserts count/best
  hold; the airtime path is the reference behavior.

- **Landed:** `18e718f` — both fields now use the same `>` guard as STATS. Refuses
  decreases only, so a late-joining watch still adopts higher totals (US6); the
  jump still registers its height, flash and vibrate, because freezing those
  would trade a wrong number for a dead display.

  **Sibling sweep inside `_jumpIsCorrupt()`:** it bounded height, airtime and
  `n` but never bounded `best_m` ABOVE — rule 4 only requires `best >= height`,
  so `best_m=9000` with a 0.5 m jump passed every check, and being a maximum
  nothing later could bring it down. Bounded to `MAX_HEIGHT_M`.

  **Acceptance:** three tests in `ModelTest.mc` — the specified reboot-reseed
  sequence, the late-join case (proving the guard doesn't block real
  increases), and the absurd-best case. **57/57 in the simulator on
  `instinct3solar45mm`.** Mutation-tested: restoring the unconditional
  assignment kills the first, dropping the `best_m` bound kills the third.

  **Bench note:** running these at all needed `JAVA_HOME` pointed at the
  Homebrew JDK — the SDK reports "Unable to locate a Java Runtime" because
  `/usr/bin/java` is Apple's stub. Recorded in `docs/bench-playbook.md`.


### [x] F-12 · **LANDED 781eabd** · major · skeptic-confirmed — no timeout out of connect states

- **Location:** `garmin/jumpfield/source/PuckLink.mc:186-194`
- **Defect:** poll() is a no-op in PAIRING, DISCOVERING and SUBSCRIBING
  (`_resumeScanAtMs` only operates in STATE_SCANNING). Garmin BLE callbacks
  are not guaranteed; a lost callback leaves the state machine permanently
  stuck with no re-entry to scanning.

### The method note that matters most

**Nine of my own tests were vacuous, misleading, or hung before mutation
testing caught them.** Every one passed first. The recurring shapes:

- A fixture that never reaches the code under test (an in-process `stats` never
  runs the parser; a two-sample append never reaches flash; a railed gyro
  inside a genuine free-fall changes no outcome).
- A stub that swallows the thing under test (`time.sleep`).
- A test with no timeout, so the mutant HANGS instead of failing.
- A monkeypatch through a shared module, leaking into the test file itself.
- **A stale `.pyc`, which makes a mutation run report whatever it likes** —
  same-length mutations survive the file being restored.

A test that has never failed has not been tested.

Added under the decision rule in `docs/audit-phase-prompts.md`: a fix that

### [ ] F-24 · minor · hand-verified — self-arm cannot bootstrap at a small lever arm

- **Location:** `sim/lever_arm.py` + `firmware/src/main.cpp:1634-1660` (the
  commit gate); exposed by `tools/tests/test_lever_arm.py`'s r=0.2 case
- **Defect:** the lever-arm estimator commits only on a VALIDATED jump, but at
  a small lever arm and high spin the flight that carries the observations is
  the one the detector REJECTS. Traced sample by sample at r=0.2 m / 600 dps,
  uncalibrated:

      t=2.925   64 observations   REJECTED    -> discard
      t=3.560    0 observations   validated   -> commit, with nothing to commit

  So the estimator never bootstraps. Larger radii work because their first
  AIRBORNE exit is itself validated.
- **Evidence:** `test_uncalibrated_device_fixes_itself_over_jumps[0.2]`, now
  `xfail(strict=True)`. It passed until F-17 only because the test was running
  the retired ungated commit policy — the same policy that corrupted
  calibration ~50×. There is no version of this that is both safe and passing
  today.
- **NOT REACHABLE ON THE DEVICE:** `JH_SPIN_SELFARM_ENABLED` is 0 — self-arm is
  compiled out for the one-shot water session. This is a design gap in a
  feature that is currently off, not a live defect.
- **Fix (not costed):** the estimator needs a bootstrap path that does not
  depend on a validated jump — e.g. accept observations from a flight rejected
  *for airtime reasons only* while still refusing the railed-gyro phantoms that
  motivated the gate. Distinguishing those two rejects is the actual work.
- **Do NOT fix by reverting the gate.** That is the ~50× corruption path, and
  the strict xfail exists so that reverting it announces itself.

### [ ] F-22 · minor · hand-verified — trace_bytes() over-reports once the region fills

- **Location:** `firmware/src/platform/nrf52/jh_store.cpp` — `trace_append()`
  accounting vs `walkTraceRegion()`
- **Defect:** the live counter adds each sample's CSV length as text arrives,
  but samples sit in an open block until it closes. Ordinarily that is a lag
  the next block write settles. Once the region is FULL it becomes permanent:
  `closeAndWriteBlock()` drops a block that no longer fits, and the bytes it
  held stay counted.
- **Evidence:** filling the region in the harness gives `TRACE_BYTES
  n=14476006` live, but a remount recomputes 14,475,206 — 800 bytes, exactly
  one 50-sample batch at 16 B/line. `TRACE_RECHECK` agrees with the remount, so
  the *stored* side is self-consistent; the live counter is the one that drifts.
- **Impact:** display only, and it self-corrects at the next boot. It reaches a
  rider as a `trace_bytes` in STATS slightly ahead of what a `dump` produces,
  at the one moment (a full region) they are most likely to compare the two.
- **Fix:** settle the counter against what was actually written when a block is
  dropped, or state in `jh_store.h` that `trace_bytes()` is an upper bound and
  make `tracecheck` the authority. Do NOT fix by making appends count only at
  block close — that would make the number lag ~5 s behind during a ride.
- **Found by:** F-08's parity work. Nothing else compares the two counters.

### [ ] F-23 · minor · hand-verified — full-chip mount is ~80× empty, and no counter scheme fixes it

- **Location:** `firmware/src/platform/nrf52/jh_store.cpp` — `walkTraceRegion()`
- **Defect:** F-08's acceptance asked for full-chip mount within ~10× of
  empty. After F-08 it is 74 ms vs 0.93 ms. The residue is not accounting: a
  floor probe with the counter replaced by a no-op still took 60 ms. The scan
  reads and CRC-checks every block in the region to find the append point.
- **Why the ticket's own fix would not have helped:** persisting cumulative
  totals in block headers removes the counting, not the walking. The walk is
  the floor.
- **Fix (real one, not costed):** find the erase boundary without decoding
  every block — a binary search over the region for the first erased page
  would be ~16 reads instead of ~19,000 blocks. This CONFLICTS with the
  deliberate torn-write behaviour of continuing past a damaged patch (a prior
  boot may have resumed appending beyond it), so it needs a design decision
  about which guarantee wins, not a local edit.
- **Impact:** bounded and already survivable — the scan feeds the watchdog
  every 64 blocks (a fix that predates this audit). It is boot latency on a
  well-used puck, not a failure.

## Refuted — do not re-chase

Raised, investigated, and killed by skeptics. Listed so agents don't
rediscover them:

- **main.cpp:1500 "double-counted jumps"** — mechanism real (unconditional
  increment), but the jumps list re-derives from flash; user-facing counts
  self-correct. Residual interface debt is F-10.
- **JumpFieldView.mc draw-loop allocation / font re-fitting** — refuted on
  cost: allocation volume is within Monkey C GC noise at 1 Hz; no retained
  growth (data layer audited at zero bytes/jump).
- **PuckLink.mc:314 puckName-inert / UUID-first matching** — mechanism
  accurate but intended: UUID-in-advert is the firmware's design; RSSI
  selection among own pucks acceptable. The timeout gap at :186 (F-12) is
  the real finding.
- **sim/windows.py Goertzel & delta-sort "O(n²)"** — reproduces, but runs on
  ~4,000-sample bench traces: milliseconds. Not worth churn.
- **trace_codec.h:156 milli_g rounding divergence C++ vs Python** — real
  divergence (32,765 float32 inputs), but every reachable input is clamped
  upstream; bit-parity holds on the reachable domain.
- **lsm6ds3_min.h two-burst read → one 12-byte burst** — contiguous registers
  confirmed, but the measured saving doesn't clear the noise floor and the
  fix breaks the accel-only fallback path.
- **"unittest discover misses tests" as a CI problem** — CI runs pytest and
  is whole; the gap is local simtest only (F-02 as scoped).
- **tools/jump:2481 nine BLE scans in `boards`** — real but bench-only
  wall-clock; the data-integrity half (F-15) is what survived.
